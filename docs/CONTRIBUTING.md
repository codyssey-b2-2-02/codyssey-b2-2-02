# Contributing Guide

> 사칙연산 구현 시 공통 인터페이스 규격은 `docs/interface.md`를 참고하세요.

## 브랜치 전략 (GitHub Flow)
- `main`: 항상 배포 가능한 상태 (= 팀 기준에서 "깨지지 않는 상태")
- `feature/*`: 작업 단위 브랜치
- 우리 팀이 GitHub Flow를 선택한 이유 (3줄 이내):
  - 수시로 배포 가능한 단순하고 빠른 릴리스 주기를 유지하기 위해
  - 복잡한 브랜치 관리 오버헤드를 줄여 기능 구현과 코드 리뷰에 집중하기 위해
  - 코드 리뷰(PR)를 필수화하여 메인 브랜치의 안정성을 항상 보장하기 위해

## 브랜치 네이밍 규칙
- 형식: `feature/<작업내용>`
- 예: `feature/add`, `feature/sub`, `feature/mul`

## 커밋 메시지 컨벤션
- 형식: `feat: [파일이름]: <요약>` / `fix: [파일이름]: <요약>` / `docs: [파일이름]: <요약>` / `refactor: [파일이름]: <요약>`
- 변경이 일어난 핵심 파일 이름(확장자 제외 가능)을 반드시 명시해야 합니다.
  - 예: `feat: add: 더하기 연산 기능 구현`, `docs: interface: 파이썬 타입 힌트 규약 추가`
- 한 커밋에 여러 수정 기능이 섞였을 때 작성 구조:
  - 원칙적으로 기능별 쪼개기 커밋(`git add -p` 등 활용)을 권장하지만, 불가피하게 한 커밋에 여러 파일/기능 수정이 포함된 경우 본문이나 제목에 각 기능별로 파일이름:요약을 명확히 분리하여 작성해야 합니다.
  - 작성 방법 예시:
    ```
    feat: 복합 연산 기능 업데이트 및 문서 수정

    - feat: add: 더하기 오버플로우 예외 처리 추가
    - fix: sub: 마이너스 연산 결과 버그 수정
    - docs: interface: 사칙연산 입출력 타입 명세 보완
    ```
- 금지 (의미없는 메시지로 간주):
  - 변경 대상을 유추할 수 없는 단어만 있는 경우 — `update`, `fix`, `temp`, `wip`, `final` 등
  - 무엇을/왜 바꿨는지 드러나지 않는 경우 — `bug fix`, `edit file` 등

## PR 규칙
- 모든 `feature/*` 브랜치는 PR을 통해서만 `main`에 병합
- 병합 조건: 리뷰어 최소 1명 승인(approve)
- PR 본문 필수 항목:
  ```
  ## 연결 이슈
  - Closes #<issue_number>

  ## 변경 사항 (What)
  -

  ## 변경 이유 (Why)
  -

  ## 테스트/검증 방법 (How)
  - [ ] 로컬 실행/간단 테스트
  - [ ] 충돌 가능성 체크(필요 시)
  ```

## 코드 리뷰 규칙
- "LGTM/좋아요"만 있는 리뷰 금지 — 라인/파일 근거의 실질 코멘트 1개 이상 필수
  - 예: 특정 라인 기반 질문, 대안 제안, 리스크 지적, 개선 제안
- 리뷰어-작성자 간 최소 1회 이상 상호작용(답글/수정 반영) 기록 남기기

## 충돌 대응 흐름
1. 충돌 발생 → 팀 채널에 공유
2. 원인 파악 (같은 hunk 수정 / 파일 이동·삭제 vs 내용 수정 등)
3. 해결 (keep both / choose one / refactor 중 택)
4. `docs/conflict-resolution.md`에 기록
